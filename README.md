## Nginx Verify Token Module

Verify a keyed BLAKE3 hash (like HMAC) and perform an action if verification fails.

The structure of the token is:

base64(timestamp + 32-byte hash)

The hashed message is:

timestamp + binary client IP address + optional extra string

The timestamp is UNIX timestamp, 8-bytes (64-bit) long, in little endian byte order.

The token can be generated by an authority in response to a successful login, solved CAPTCHA or the like.

## Directives

### verify_token_secret
* **Default**: none
* **Context**: http, server, location

32-byte secret key, in hex.

### verify_token_secret_alt
* **Default**: none
* **Context**: http, server, location

32-byte secret key, in hex. If verification fails with the first secret and this is set, verification will be attempted with this secret. Can be useful for key rotation.

### verify_token_extra_str
* **Default**: none
* **Context**: http, server, location

Extra string appended to the hashed message. This can be used to grant access to different things with the same secret key.

### verify_token_cookie
* **Default**: none
* **Context**: http, server, location

Name of cookie containing the token to be verified

### verify_token_verify
* **Default**: none
* **Context**: http, server, location

Directly supply the token to verify, presumably using variables ($http_xxx, $arg_xxx for headers or query string arguments)

### verify_token_expiry
* **Default**: 3600 seconds (1 hour)
* **Context**: http, server, location

The token is deemed valid for the duration of this time period after the timestamp. Can be specified in nginx time interval format, e.g. `1h`, `7d`, `2w` etc.

### verify_token
* **Default**: none
* **Context**: http, server, location, location if, limit_except

**Usage**:

* **Disable:** `verify_token off;`
* **Redirect to named location:** `verify_token @challenge;`
* **Redirect to location:** `verify_token /challenge;`
* **Respond with HTTP redirect:** `verify_token 303 /challenge;`
* **Respond with any HTTP status code:** `verify_token 403;`

Takes one or two arguments, both can contain variables.

If the first argument is `off`, this directive is disabled.

Try to verify a token provided in `verify_token_verify` if set, or contained in the cookie named by `verify_token_cookie`.

If verification fails, perform the specified action: either an internal redirect or an HTTP response. If the HTTP status code is one of 301, 302, 303, 307, 308 and an extra argument is provided, the extra argument is placed in a `Location` header, providing the redirect destination.

HTTP redirect behavior is further controlled by Nginx core module directives `absolute_redirect`, `server_name_in_redirect`, and `port_in_redirect`.

For internal redirects, named locations can perform better.

### verify_token_add_header

* **Default**: none
* **Context**: http, server, location, location if, limit_except

**Usage**:

* **Disable:** `verify_token_add_header off;`
* **Add header:** `verify_token_add_header name value [always|valid|invalid|expiring ttl] [status ` *`code`* `...];`
* **Set cookie:** `verify_token_add_header cookie;`
* **Set cookie:** `verify_token_add_header cookie "" [always|valid|invalid|expiring ttl] [status ` *`code`* `...];`

Can be used multiple times.

Takes one, two or three arguments. The first two can contain variables.

If the first argument is `cookie`, a valid token is generated and sent to the client in a cookie according to the configured cookie name, secret, and expiry, as follows: `Set-Cookie: $name=$token; path=/; max-age=$expiry; Secure`

Otherwise the first two arguments are taken as a header name and value to be sent to the client.

**Condition**: You may specify conditions when to add the header.

Token validity: `always`: regardless of token validity, `valid`: only when verification succeeds, `invalid`: only when verification fails, `expiring`: A TTL time value must follow. Add header when verification fails, or the token is valid but its remaining validity period is equal to or less than TTL. The default is `invalid`.

HTTP status code: `status`: when the HTTP status code matches one of the listed values. You may specify one or more value.

Note: If you use `cookie` and you want to set conditions, set any value (such as the empty string) in place of the header value (the second argument).

## Variables

### $verify_token_result

When this variable is used, verification is attempted according to the configuration, as described for the [verify_token](#verify_token) directive. If a token is found and is valid and not expired, the value of this variable would be `1`, otherwise `0`.

### $verify_token_token

Evaluates to a valid token using the currently set secret. The hashed message consists of the current timestamp, the client's binary IP address, and `verify_token_extra_str` if set.

### $verify_token_escaped_uri

The URI, escaped with NGX_ESCAPE_ARGS: spaces and `# % & + ; ?` are escaped.

### $verify_token_escaped_uri_component

The URI, escaped with NGX_ESCAPE_URI_COMPONENT: only alphanumeric and `- . _ ~` remain unescaped.

### Configuration Examples

```nginx
server {
	verify_token_cookie let_me_in;
	verify_token_secret 00000...;

	if ($permit_country) {
		break;
	}

	set $token_redir @challenge; #remains unset for permitted countries

	verify_token $token_redir;

	location @challenge {
		verify_token off;
		root /srv/www/captcha;
		add_header X-Robots-Tag none;
		add_header Cache-Control "no-store, no-cache, must-revalidate";
		try_files /index.html =404;
		# location.reload() once you got your token
	}
	location ^~ /.challenge-static/ {
		verify_token off;
		root /srv/www/captcha;
	}
	location ^~ /.challenge-api/ {
		verify_token off;
		proxy_pass http://localhost:8080/api/;
		proxy_set_header X-Real-IP $remote_addr;
		# upon success, upstream app will send a token
	}
	location / {
		# ...
	}
}

server {
	verify_token_cookie let_me_in;
	verify_token_secret 00000...;

	location /challenge/ {
		proxy_pass http://localhost:8080;
		if ($upstream_http_x_status = OK) {
			verify_token_add_header cookie;
		}
	}
	location / {
		verify_token 403;
		# or
		verify_token 303 /challenge/;
	}
}
```

### Dependencies

The [C BLAKE3 implementation](https://github.com/BLAKE3-team/BLAKE3/tree/master/c). On Debian, `libblake3-dev` for building and `libblake3-0` for runtime. At the time of writing, these packages are in the testing distribution.
